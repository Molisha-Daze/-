## Android 习惯打卡 App — 静态 QA 报告复核

复核了外部 GPT 对 `android/` 工程的 6 条静态分析结论，逐条回到源码验证，产出
`android/QA复核与修复方案.md`。

**复核结论**
1. 编译阻断 ✅ 属实 — HistoryScreen:57-58/82 引用 ViewModel 不存在的
   `allHabits` / `allCheckIns` / 两参数 `toggleCheckIn`。Repository 里已有对应
   Flow，只是没转发到 ViewModel。
2. 未来日期可打卡 ✅ 属实 — 报告漏报「切月后 selectedDate 不与月份联动」，
   导致月历高亮与下方计划清单显示不同日期。
3. 排期/计数器未落地 ✅ 属实 — `isHabitScheduled` 是 CalendarMonthView 的
   private 函数，今日页/统计调用不到，靠默认值侥幸对齐。今日页、月历、
   通知「一键完成」对计数器有三种不同完成语义。
4. 提醒链路 ⚠️ 结论对机理不准 — CheckInActionReceiver:30 其实查了 habit，
   但只取字段不判空；真正崩点是 CheckIn 的 `ForeignKey(onDelete=CASCADE)`。
5. 破坏性迁移 ✅ 属实 — 另叠加 `exportSchema=false`，将来无法用 AutoMigration。
6. 权限无反馈 ✅ 属实 — 但报告把 SCHEDULE_EXACT_ALARM 与 USE_EXACT_ALARM
   混为一谈；Android 13+ 声明 USE_EXACT_ALARM 后 canScheduleExactAlarms() 恒 true，
   降级只在 API 31-32 发生。

**补充发现的 3 个隐患（报告未提）**
- A. `HabitDao.insert` 用 `OnConflictStrategy.REPLACE` + FK CASCADE →
   若以已存在 habit 走 insert 路径会连带删光该习惯全部打卡记录。建议改 IGNORE。
- B. 通知 ID / PendingIntent requestCode 靠 `habitId.toInt()` 与 `+100000` 偏移
   散落在三个文件，应集中在 NotificationHelper 生成。
- C. 计数器无 +1 入口，`toggleCheckIn` 只能 0↔1 横跳，App 内永远无法把
   目标 >1 的习惯标记完成。

**待拍板**：问题 3 走方案 A（完整实现排期+计数器 UI，需先把 isHabitScheduled
提取到 util/HabitSchedule.kt 共用）还是方案 B（砍字段收敛为纯每日习惯）。
version=1 尚未发布，现在改实体不需要写迁移。

## 方案 A 实施（同日 10:20）

用户拍板走**方案 A**，六条结论 + 三个补充隐患全部落地。核心改动：

- **新增 `util/HabitSchedule.kt`**：`isScheduled` / `isCompleted` / `effectiveTarget`
  / `currentCount` 成为唯一权威判定，月历、今日页、热力图、通知共用。这是根治
  「今日页/统计/月历三处口径打架」的关键。
- `HabitWithStats` 增 `scheduledToday`；ViewModel 增 `todayHabits`（今日页用），
  `habitsWithStats` 保留全量给「习惯管理」页。
- `AddEditHabitDialog.onSave` 改为回传**完整 Habit**；新增重复方式（每天/每周/
  每月/每N天/单次）、起止日期、计数器开关。
- 计数器：`incrementCheckIn` / `decrementCheckIn`；`toggleCheckIn` 对计数器转发
  递增；HabitCard 与月历清单均提供 ±。
- 未来日期三道防线：月历禁翻未来月 → 未来格只读置灰 → 数据层 `isWritableDate()`
  拒绝；`StreakCalculator` 过滤未来日期。
- 提醒链路：`AlarmReceiver` 先查「今天没排期/已完成」再决定弹不弹，且用 DB 最新
  名称而非 intent 里的旧名；`CheckInActionReceiver` 补 habit 判空 + archived 校验
  （否则 FK CASCADE 抛 FOREIGN KEY constraint failed）；完成后 `cancelNotification`。
- `HabitDao.insert` REPLACE → IGNORE；通知 ID/requestCode 集中到 `NotificationHelper`。
- Manifest 删除 `USE_EXACT_ALARM`（它安装即授予不可撤销，会掩盖降级提示）。

**踩坑记录**：
1. 老数据 `startDate` 是空串，语义为「不限起始」。编辑弹窗若擅自填成今天，
   该习惯在开始日期之前的全部历史排期会消失 → 弹窗对空值显示「不限」并原样保留，
   且上下界比较在 start 为空时跳过。
2. `endDate` 与空 `startDate` 比较时 `"" < "2026-09-19"` 恒真，会误报
   「结束日期不能早于开始日期」，已加 `startDate.isNotBlank()` 前置。
3. Write 工具在跨轮次后可能报「File has not been read yet」，重新 Read 一次即可。
4. Edit 时 old_string 若比 new_string 多带一行，会**静默删掉那一行**（本次误删了
   `Book` 图标 import）。改 import 块务必确认前后完整。

**未验证**：本机无 Android SDK / Gradle wrapper，未编译。首次构建跑
`./gradlew :app:assembleDebug`，会生成 `app/schemas/1.json`，需纳入版本管理。

### 追加修复的 3 条
1. **连续打卡算法改为排期感知**：`StreakCalculator.calculate` 签名从
   `(Set<String>, LocalDate)` 改为 `(Habit, Map<String,CheckIn>, LocalDate)`。
   先按 startDate..today 生成「有排期的日期」序列，再在该序列上跑最长/当前连续；
   「最后一次排期是今天且未完成」时跳过今天（今天还没过完不算断签），
   若最后一次排期在过去且未完成则归零。月/周/间隔计划不再被没排期的日子打断。
2. **数据层补排期校验**：`isWritableDate(date)` → `canWrite(habit, date)`，
   同时校验「非未来」+ `HabitSchedule.isScheduled`。toggle/increment/decrement/
   attachPhoto 全部走它。`CheckInActionReceiver` 增加「今天是否排期」校验，
   未排期则撤掉残留通知并不写库（防通知 Action 重放）。
3. **精确定时状态即时刷新**：「去设置」改为 `rememberLauncherForActivityResult(
   StartActivityForResult())`，返回后才查 `canScheduleExactAlarms()`；
   另外加 `DisposableEffect(LocalLifecycleOwner) + LifecycleEventObserver(ON_RESUME)`
   兜底。原代码是 `startActivity` 后立刻查询，查到的必然是旧状态。
